## 1. 当前 AI 识别链路

1. 从静态目录和当前场景 item 资产合并可用资源，同 ID 时内置目录优先。
2. 生成按 category 分组的文字摘要。逐项包含 ID、原名称、宽高深、attachTo、tags。
3. 大语言模型根据用户请求选择 catalogSlug；提示词要求工具参数使用英文。
4. 本地解析器先匹配准确 ID，再匹配忽略大小写的名称，再进行关键词模糊匹配。
5. 添加校验处理场景、尺寸、挂载和空间约束；布局优化器调用 getPlacementMeta(asset.id, asset.category)。
6. 摆放元数据按定义顺序，取 ID 或 category 包含的第一个关键词。该层不使用 name、中文名称或 tags。

这解释了为何办公桌 tags 含 desk，却没有命中 desk 规则；休闲椅含 armchair 标签，也不意味着会用 armchair 规则。目录 tags 会进入给大语言模型的摘要，但不会因此进入摆放元数据匹配。

主要依据：[目录解析器](../../../packages/editor/src/components/ai/ai-catalog-resolver.ts)、[摆放匹配](../../../packages/editor/src/components/ai/furniture-placement-metadata.ts:339)、[优化器调用](../../../packages/editor/src/components/ai/ai-layout-optimizer.ts:98)、[校验与优化调用](../../../packages/editor/src/components/ai/ai-mutation-executor.ts:263)。

## 2. 已复现问题及其影响

### A01：两张餐桌发生名称索引覆盖

`dining-table-mo9ms5yh` 的英文名是 `Dining table`，`dining-table` 的英文名是 `Dining Table`。目录中的原始名称并不完全相同，但名称索引转小写后共用一个 key，后者覆盖前者。

对前者使用原英文名查询，会返回后者 ID。准确 ID 查询均正确。这不是“模型文件丢失”，而是名称不能被当作唯一键。

入库要求：系统生成稳定 ID；同名可并存；名称检索返回候选集合；最终执行必须带确定的 ID。

### A02：规则顺序影响模型行为

| 资产 | 实际首条规则 | 其他命中 | 判断 |
| --- | --- | --- | --- |
| bookshelf | bookshelf | shelf | 具体规则优先，当前合理；不能把多命中本身视为缺陷 |
| bedside-table | side-table | bed、bedside | 床头柜套用客厅边桌规则，专属规则未生效 |
| floor-lamp | lamp | floor-lamp | 自由放置先于落地灯角落规则 |
| shower-rug | shower | rug | 浴室地垫套用淋浴角落规则 |
| kitchen-cabinet | cabinet | kitchen-cabinet | 前方净空为 0.6 米，后置厨房规则的 0.9 米未生效 |

此外，`toilet-paper` 命中 toilet，`sunbed` 命中 bed，按名称含义存在误继承风险；本次没有视觉验收，不把风险表述为已发生的最终摆放错误。

入库要求：分类有稳定语义 ID，安装和放置规则显式绑定。关键词可作为旧资产迁移建议，不能永远承担执行规则分派。

### A03：75 个模型使用通用摆放规则

DEFAULT 为自由放置、任意朝向，前后左右净空分别为 0.3、0.1、0.1、0.1 米。部分装饰物使用通用规则可能足够，办公桌、衣柜、设备等则需要按实际用途复核。

这不是 AI 只能认识 36 个模型，也不是 75 个模型无法放置。111 个模型都在摘要中；这个统计只针对 getPlacementMeta 的专用规则覆盖。

### A04：五个吊顶物件收到“必须有墙”提示

recessed-light、ceiling-lamp、sprinkler、smoke-detector、ceiling-fan 的 attachTo 为 ceiling，但摘要统一附加 `MUST have wall`。执行器另有吊顶校验，不能据提示词问题断言最终一定放错。

入库要求：挂载规则与 AI 描述共用同一结构，区分墙内、墙侧、吊顶和物体表面。

### A05：中文 UI 搜索和底层 AI 解析不是同一个能力

111 项的中文 UI 名称搜索都能匹配自身。直接将这些中文显示名传入 resolveCatalogSlug，只有两个带英文/数字词的汽车名称能解析到自身，其余 109 项未匹配到自身。

这不是“真实 AI 中文识别失败率为 109/111”。真实对话会先经过大语言模型翻译/选 ID，本次没有请求外部模型。统计说明本地解析器没有直接使用中文字典。

入库要求：中文名、英文名、别名进入共享检索，稳定 ID 不要求由用户命名或翻译。

### A06：两套目录同 ID 尺寸不一致

例如电视柜在编辑器为 `[1.86, 0.35, 0.32]`，MCP 为 `[2, 0.4, 0.5]`；单人床分别为 `[1.08, 0.6, 2.14]` 与 `[1.5, 0.7, 2.5]`。23 项对照全部保留在工作簿中。

两套地址不同，可能使用不同处理版本。未比较字节或测量几何，不能宣布某一侧正确。共享目录迁移前应核对同 ID 是否确实代表同版本资产。

### A07：建议分类和实际分类存在差异

回退推荐的 categoryKeywords 额外包含 decor、lighting，而实际目录没有这两个 category。某些查询可能进入没有资产的推荐类别。它们也不应直接被算入现有分类表。

### A08：不明确的查询会被自动替换为具体模型

| 原函数输入 | 原函数结果 | 匹配类型 |
| --- | --- | --- |
| unknown-model-zzzz | tesla | fuzzy，因名称中 Model 等词发生重叠 |
| wall-light | recessed-light | fuzzy，无形状告警 |
| round-dining-table | dining-table-mo9ms5yh | fuzzy，有“圆形版本不存在”的形状提示 |

这是解析器直接调用结果，未将这些结果写入场景。搜索阶段可以宽松，创建阶段应要求准确资产 ID。形状或安装方式不满足时应返回候选/无结果，而不是自动选最近项。

### A09：目录卡片的创建能力没有完整传给 AI

`cabinet` 条目带 `tool: cabinet`，模型库点击走专用橱柜工具；AI `add_item` 在确认操作中通过 ItemNode.parse 创建普通物件。AI 摘要没有 tool 字段。

同时，`cabinet` 与 `kitchen-cabinet` 共享一个 GLB 地址，因此全目录为 111 个条目、110 个不同 src。它们不能仅根据相同地址合并，因为 UI 创建能力不同。

依据：[模型库工具选择](../../../packages/editor/src/components/ui/item-catalog/item-catalog.tsx:84)、[AI 创建普通 ItemNode](../../../packages/editor/src/components/ai/preview/confirm-operations.ts:157)。

入库要求：单独登记资产表示方式和创建能力。普通网格、参数化节点、组合资源不能仅凭分类名互相替代。

12 个模型另有专项复核备注。例如：

- cactus 的标签同时出现 rack/hanger/storage/sculpture，不能据名称“仙人掌”直接认定为植物。
- ball 带 sphere/sculpture/garden 标签，不能直接认定为运动球。
- KALLAX 的 ID 含 1x4，当前中英文名称指向 2x4；保留 ID，规格需按实物核对。
- column/pillar 是目录中的网格物件，不能等同于原生结构柱节点。
- fire-detector/ev-wall-charger 的 wall 挂载需要核查是否实际应为 wall-side。

类目粒度可以继续调整，比如影音设备下面是否再细分电视和音箱。应根据查找需要和不同规则来拆分类别，而不是为了每个名称都拥有一个专用叶子。

## 4. 从盘点得出的入库契约

| 信息 | 主要负责方 | 本次证据 |
| --- | --- | --- |
| 资产 ID / 分类 ID | 系统生成并保持稳定 | 餐桌同名覆盖说明名称不是可靠键 |
| 中英文显示名与别名 | 用户输入，AI 辅助 | 现有中文界面映射未进入底层解析 |
| 功能分类 | 用户选已有分类，AI 推荐 | 五个旧分类混合维度，functionTags 尚未启用 |
| 尺寸和校正 | 程序测量，异常时用户确认 | 当前登记值和 MCP 值不一致，不能继续盲信默认值 |
| 安装/放置规则 | 规则模板建议，按模型校验 | 子串匹配会继承错误行为 |
| 创建与交互能力 | 系统明确注册 | cabinet 显示与 AI 创建路径不同 |
| 文件和版本 | 入库服务持久化 | 目录条目与文件地址并非一对一；同 ID 也可能存在不同版本 |

用户可以主要通过逐级选择分类和命名完成操作，但上述字段须由系统在后台完成或核验。新建一个分类仅产生语义和默认规则，不会自动增加新的参数化或交互能力。

建议新分类的最小定义：稳定 ID、父级 ID、中文名/可选英文名、用途说明、别名、能否直接归属资产、可继承的规则模板。需要多种安装方式的类别不能强行继承同一个安装值。空间、形状、环境、风格等保留为独立属性，避免分类树无限扩张。

旧 category 和 ID 在迁移期保留。新增功能映射经评审后发布，再让 UI 搜索和 AI 共同消费。分类发布触发目录版本更新；执行前校验具体模型与创建能力，不再依赖临时翻译的名称猜测。

- 111 个资产分类草案覆盖检查，无重复 ID、遗漏或额外 ID；62 个分组和现有五类数量核对。

源码快照以 audit.json 的 sources 哈希为准。git HEAD 只标识提交基线，不能代替包含未提交变化的实际源文件哈希。

## 6. 后续实施优先级

1. 固定精确 ID 执行及多语言候选检索，消除静默模糊替换和名称覆盖。
2. 明确普通网格与专用工具能力，特别是 cabinet，避免表面上“找对名称”但创建不同对象。
3. 先修正已确认的挂载摘要与规则分派问题；75 项通用规则按用途复核，不一律判错或一律新增规则。
4. 评审分类草案与 12 个专项复核项，用少量实际模型完成尺寸/朝向/挂载测量试点；核对 MCP 对照资产。
5. 统一资产发布、缓存更新和资源持久化后，再接入批量上传及 AI 辅助填表。AI 生成的分类与名称同样遵守以上契约。

本报告是后续分类和入库开发的现状基线。它不要求用户重新手填 111 条资料，也不将讨论草案直接应用到已有项目。
