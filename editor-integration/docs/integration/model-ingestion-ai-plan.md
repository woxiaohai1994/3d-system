# 模型入库与 AI 识别方案

日期：2026-09-20。状态：调研与实施建议，已补充资产盘点结果、分类管理、材质方案与原位替换要求；本文不代表功能已实现。

目标：新增模型经一次规范入库后，模型库、中文/英文搜索和内部 AI 使用同一条资产记录；AI 能发现模型、选择正确型号、按规则放置，并在保存重开后继续使用。AI 识别无法承诺对任意模型和任意说法百分之百正确；系统应保证资料可追溯、调用可校验、歧义不静默替换。

本次依据当前源码及官方技术文档，不以旧记录代替现场代码。不调用已配置的付费 AI，不修改场景，不代表完成模型渲染或真实厂商请求验证。

## 2. 推荐方案与范围

建设“统一资产目录 + 模型入库向导 + AI 资料助手”。模型发布一次，界面、搜索、内部 AI 读取同一版本。保留现有模型 ID、场景对象、渲染器、AI 配置和场景预览/撤销流程。

第一版支持静态、独立、可复用的 GLB 物件。GLB 仍须检查外部纹理/缓冲引用，不能根据扩展名假定资源完整。后续支持含完整依赖的 glTF 资源包。FBX/OBJ/Blend 转换和生成全新三维网格不作为首版前置条件。

墙、楼板、程序化橱柜等继续使用现有节点和专用工具；不转成普通 GLB 后冒充可参数化对象。包含多个物件的整屋模型先标记为组合/参考资源，拆分或确认整体用途后再发布，避免整屋被识别为一张桌子。

这里的“AI 快速添加”首先指辅助导入已有三维资源、生成资料和规则建议。AI 生成新的三维网格可日后对接独立服务，生成结果仍必须走同一入库管线。

## 3. 用户实际如何添加模型

在现有模型库提供一个“添加模型”入口，支持拖入单个或多个 GLB。聊天里的“帮我加入模型库”打开同一批次，不建立第二套上传流程。

1. **拖入文件。** 建立可恢复的导入草稿，计算内容 hash，检查重复、依赖和格式。默认进入“我的模型”，目录作用域不跟当前场景的存亡绑定。
2. **自动检查和预览。** 读取几何及纹理统计、计算边界，生成主缩略图、俯视图和若干视角图；提供旋转、尺寸校正和落地校正。
3. **AI 补全资料。** 用户可补一句“这是吊装灯”或“这是四人圆餐桌”；AI 根据说明、文件线索和可用视图建议中英文名称、用途、别名、分类与特征。
4. **集中处理不确定项。** 展示识别结果和待处理项，如“餐桌/茶几不确定”“安装方向待确认”。字段可直接编辑；已由人确认的值不会被再次识别覆盖。
5. **加入模型库。** 对选中且符合发布条件的条目批量发布。数据发布成功后同步界面和 AI 目录，明确显示“可供 AI 使用”；失败条目留在草稿中单独重试。
6. **试用。** 提供“让 AI 试摆”操作，沿用现有场景预览、确认、撤销，入库本身不在场景里偷偷生成实例。

建议向导保持“上传—检查—入库”三个主要步骤；名称/用途/尺寸为常用项，变换、挂载与高级语义折叠展示。批量模式支持按类别填充、只看待处理条目、取消和失败重试。

没有 AI 配置仍可上传、校正、手填与保存草稿，只有点击 AI 补全时引导配置，并保留当前内容。纯文字配置可以先完成资料整理；未支持视觉时不能标记“已看图识别”。

## 4. 统一资产记录：稳定编号与多语言展示分开

建议新增版本化 `AssetDefinition`，由核心层定义纯数据契约。目录服务存储完整定义，投影为现有 `AssetInput` 交给渲染与摆放。新增语义字段不能直接塞入现有 Zod 对象后假设会被保留，必须声明 schema、序列化和迁移路径。

| 字段组 | 建议内容 | 主要来源 |
| --- | --- | --- |
| 身份与版本 | assetId、assetVersion、schemaVersion、contentHash、状态、作用域 | 系统生成；旧模型保持原 ID |
| 文件 | 原始文件、可渲染派生文件、预览图、依赖清单、各自 hash、来源信息 | 导入管线 |
| 多语言 | labels.zh-CN/en、description.zh-CN/en、aliases.zh-CN/en、原始文件名 | 用户原文与 AI 翻译建议 |
| 语义 | 受控 category/functionTags、用途、房间类型、形状、外观材质、风格、颜色、可选座位数 | AI 建议 + 人工校正 |
| 几何 | 原始边界、最终 dimensions、校正 scale/rotation/offset、坐标约定、正面朝向 | 几何计算 + 人工校正 |
| 放置 | 地面/墙内/墙侧/吊顶/物体表面、锚点、是否靠墙、操作净空、承载表面 | 显式规则 + 模板建议 |
| 能力 | 普通静态资产或专用节点/工具；可用交互能力 | 系统适配能力，AI 不得猜造 |
| 产品与款式 | 可选产品组、同款变体关系、几何资产引用、材质方案；与资产文件修订版本分开 | 用户确认 + 导入资料 |
| 材质部位 | 稳定部位 ID、中英文标签、默认材质、允许覆盖范围、部位映射及检测状态 | 文件扫描 + 人工适配 |
| 质量与证据 | 文件检查、渲染检查、字段来源、待确认字段、规则版本、AI 配置标识 | 入库管线 |

多语言原则：

- `assetId`、类别枚举、工具参数键不随界面语言变化。旧英文 slug 保持不动；新资产用稳定唯一 ID，可带可读英文段，但不依赖名称唯一性。
- 用户可只填写中文，AI 辅助补英文和别名；不要求用户手工起英文名字。没有英文时可保留缺省并用已有名称回退，不伪造译文。
- 中文“餐桌”、英文“dining table”和同义词都搜索同一记录，最后执行只使用同一 assetId。
- 展示名称和场景实例的用户自定义名称分开。语言切换不改实例名、尺寸或参数；人工改名也不破坏资产引用。
- 材质区分“木纹外观”与“真实橡木材质”，后者需要来源资料。看图无法确定的属性保留未知，不用默认值冒充事实。
- 不同几何/尺寸的款式分别登记并保留关系；仅换材质时优先复用几何与材质方案。同字节文件可提示复用，不能单凭相同名字认定重复。

语义示例：同一模型保留 ID `round-dining-table-xxxx`，中文名“四人圆餐桌”、英文名“Round Dining Table”，别名包含“圆桌、餐桌”，功能 `dining-table`、形状 `round`、尺寸 `[1.2, 0.75, 1.2]`。尺寸必须来自校正后的测量，四人用途来自用户确认或可追溯建议。示例为建议的数据内容，不是现有 schema 已支持的新字段。

### 4.1 分类可以扩展，执行能力不能只靠名称扩展

既有分类按层级逐步选择，允许归属到明确可收录资产的中间节点，不要求每次填满固定三级。分类 ID 由系统生成，中文/英文标签和别名单独保存；移动、重命名分类不能改变其 ID 或破坏旧资产引用。

新增分类时先检查现有同义分类、父子循环和重复路径；显示拟继承的放置模板及默认属性。单用户首版允许用户自行创建并确认，暂不引入组织审批流程。标签相似只提示复用，不自动合并分类；分类合并应迁移引用，删除被使用的分类前必须指定归属。

分类描述“是什么”，风格、颜色、材质、房间和款式关系作为并列属性，不逐层堆成分类树。AI 可以建议父分类和属性，但不能自己创造系统尚不支持的宿主、工具或交互能力。新分类使用已支持的能力时可直接接入检索；需要新能力时明确标记待适配，不能显示为已支持。

系统生成分类、产品组、资产、场景实例各自的编号。不同款式共享产品组不代表共享资产 ID；原位换款保留场景实例 ID，也不意味着覆盖旧资产文件。

## 5. AI 辅助入库如何复用现有能力

### 5.1 文字辅助可以先接入

复用现有 profile、服务端密钥保存、厂商协议、取消与错误处理。增加专用的元数据草稿请求，输入用户说明、原始名称、可用几何信息和受控分类表，返回结构化建议。

入库请求不携带整套建房/改场景工具。它只生成 AssetMetadataDraft，不能修改文件地址、已测几何、资产 ID 或发布状态。服务端用 Zod 等契约检查枚举、长度与格式。支持厂商的原生结构化输出时使用；不支持时解析 JSON 并校验，失败保留草稿供编辑，不能假设所有兼容接口都支持同样参数。

### 5.2 多视图识别需要补的接口

在现有配置体系内增加 `vision` / `structuredOutput` 的能力状态（未知、支持、不支持，附核查来源），按具体配置、模型及端点判定。接口协议兼容并不意味着模型支持图片。

支持视觉时，优先复用当前配置；当前配置不支持时，允许选用另一条已保存的视觉配置。不得静默改换厂商。初期优先打通一条经真实验证的视觉适配路径，再扩展其他协议；AI 主聊天仍可沿用当前文字模型。

建议新增独立 `asset-metadata` 服务端请求契约和路由，复用协议底层，但不让场景 revision 成为草稿分析的前提。图像使用服务端可验证的临时资源 ID/字节；浏览器 blob URL、asset:// 地址和 localhost 地址不能直接发给远端 AI 当成可读取图片。图片大小和数量使用独立预算，避免突破现有文本请求体限制。

自动生成主视、背视/侧视、俯视等 3—4 张预览，按对象复杂度补视角。AI 输入包含视角标签和测量数据；尺寸仍以几何校正为准，不由 AI 看图估算。无需将完整高精度网格上传给对话模型。

保留每个字段来自用户、测量还是 AI 建议的标记，记录模型配置标识、提示词版本和输入 hash，不记录密钥。AI 自报信心不视为校准概率；是否需要复核优先依据缺字段、规则冲突、候选歧义和测量异常。

对相同文件 hash + 校正配置 + 识别规则版本复用结果；用户主动重新识别时才重新请求。小批并发、限流、取消、失败重试和人工锁定字段均纳入批处理。

## 6. 几何、放置与持久化

### 6.1 几何和挂载

glTF 采用米制、Y 轴向上。仍须检查作者是否按约定导出：错误单位不能仅靠文件声明发现。尺寸异常时让用户选择单位或输入已知尺寸，再重新生成边界和预览。

复用现有 GLTF/KTX2/Meshopt 加载能力，保持校正变换与渲染器使用的顺序一致。普通落地模型可建议底面居中，挂墙和吊顶模型使用对应挂载锚点，不能全部强制落地。正面不能仅凭最长轴决定。

`dimensions` 定义为校正变换后的资产基准尺寸；场景实例缩放另计，避免双重缩放。检查场景摘要、碰撞/净空计算是否使用实例实际尺度。本次未对全部实例缩放路径做验证，列为实施核查项。

现有 `attachTo` 只含 wall/wall-side/ceiling；新的放置语义要由适配器明确映射，不能直接添加 `attachTo: floor` 破坏现有契约。`surface.height` 只表示简化承载高度，不足以描述任意凹形或多层表面；首版使用有明确平面承载面的模型。

修正当前摘要中所有 attachTo 都附加“必须有墙”的提示。墙内、墙侧、吊顶和桌面分别生成规则；缺少对应宿主时先找宿主或询问，不改用不相干模型。2D 和 3D 采用相同放置规则。

### 6.2 存储与版本

推荐延续当前本地优先架构：宿主数据目录保存原始文件和派生文件，SQLite 保存资产定义、版本、作用域、导入任务和目录 revision。第一版不要求另建云服务。IndexedDB 可用于临时上传/预览缓存，不能成为跨浏览器与导出时唯一的资源副本。

采用先写临时文件并验证、再原子迁移文件、最后事务发布数据库记录的顺序。崩溃可以留下待清理的孤立文件，但不能发布一个文件尚未落盘的“可用模型”。发布以 importId/hash 幂等，失败不产生重复目录项。

通过受控宿主资源路由读取文件，并接入现有 URL 解析层；相对 `/api/assets/...` 路径不能被现有 CDN 逻辑错误拼接到远程域名。文件路径不由用户名称直接拼接。

新场景实例保留资产 ID、版本、文件引用及必要运行时快照。修改目录资料或发布新模型版本不自动替换旧场景实例。下架阻止新调用，保留旧场景所需版本；清理需考虑场景、历史、导入任务和导出引用。

项目导出必须携带资产清单和所需资源字节，或明确选择联网引用模式；不能承诺仅有场景 JSON 的文件在其他电脑离线打开。现有项目包 ADR 只是设计依据，相关打包能力须另外核实并实现。干净浏览器配置和另一台环境重开是验收条件。

### 6.3 同款材质、不同款式与原位替换

“白色壁炉换成石材”和“换成另一种造型的壁炉”采用不同操作。分类相同不代表同一产品；产品组为可选关系，不能把全部壁炉强行合成一个产品。材质方案是设计外观，除非有来源资料，不能据此声称它是厂商真实在售规格。

**材质切换：** 保留几何、场景实例 ID、位置和归属，切换指定部位的材质引用。入库扫描输出实际可换部位及标签，UI 和 AI 共用。没有材质槽的模型先标记为未适配；可由适配工具和用户选定网格/材质建立部位，但不得凭 AI 猜测的名称发布可用能力。缺少 UV 或其他必要数据时，区分纯色可用与贴图不可用，不能承诺换材质都保持正确纹理效果。旧部位 ID 不因中文标签变化而改变。

修正 AI 工具描述、场景摘要、校验器和渲染器之间的差异：`update_material` 不再声称可整体重涂任意 GLB；`paint_slot` 必须校验目标实际部位以及材质引用。未检测部位时提示先适配，未知部位必须报错，禁止记录了覆盖但画面没有变化却显示成功。

**原位替换：** 新增独立的替换命令，由模型面板和 AI 共用。首版限于通过兼容检查的普通静态 GLB；参数化节点、跨安装方式、带交互或无法迁移附着物的替换明确说明限制，不能静默降级。

- 保留实例 ID、用户名称、集合、楼层及适用的宿主关系；替换目标绑定准确资产 ID 和版本。
- 默认使用新款的校准尺寸，保持朝向，按底部/背面/安装锚点对齐。不能简单复制位置后假定不悬空、不穿墙；非均匀拉伸不得作为默认适配方式。
- 如果用户要求保持原宽度，作为明确选项按比例缩放并重新校验尺寸、净空与宿主。不能为了尺寸相同任意改变产品比例。
- 旧材质仅在有明确兼容部位映射时继承，否则预览新款默认方案。显示哪些自定义材质无法继承。
- 物件上的附着物、承载关系、墙体开口等受影响内容必须重新校验。首版无法可靠迁移时阻止替换并说明原因，不丢弃子对象。
- 预加载并确认目标资源可用，预览通过后一次事务提交；取消或加载失败保留旧对象。撤销/重做、保存重开及 2D/3D 必须得到一致结果。

替换不是目录文件覆盖，也不是 AI 自行拼接删除与新增。发布一个资产修订版本不自动升级场景；用户明确替换时才改变实例绑定。

## 7. 如何让 AI 稳定找到、选对并使用

### 7.1 统一读取和变更通知

建立共享 CatalogService，提供 list/search/getById/getVersion/subscribe，内置目录作为种子源，自定义发布记录作为持久化源。UI 的 items/searchResults 与 AI 的 CatalogProvider 适配到同一服务；MCP 通过无 React 的共享数据接口读取，不依赖编辑器包。

每次发布/下架使 catalogRevision 递增，仅使相关缓存失效。项目切换更新作用域，手动“刷新模型”保留为恢复入口，不后台反复扫描磁盘。AI 搜索与预览记录实际使用的资产版本；提交前检查该版本仍可用。目录其他条目变化不应无故令全部预览失效。

场景中未登记的资产可显示为“仅当前项目”，通过明确“保存到模型库”晋升为持久化记录。不得自动把场景中的私有/临时资源发布为公共库；ID 冲突要明确处理，不能静默覆盖。

### 7.2 从全量提示词过渡到检索工具

当前摘要有 64,000 字符契约上限；模型大量增加后不宜继续把全部资料塞进每轮提示词。建议新增只读工具：

- `search_assets(query, filters, cursor)`：支持中文、英文、别名、用途、尺寸、安装类型等条件，返回少量候选及命中理由、ID、版本。
- `get_asset(assetId, version)`：返回选定模型完整使用规则与预览引用。
- 添加模型继续使用现有 `add_item(catalogSlug=assetId, ...)`；执行器解析精确记录并检查可见性、可用版本、资源与放置条件。

工具需要贯穿定义、工具名白名单、请求/返回校验、流式解析、agent loop 调度和工具结果回传；只新增工具描述不足以完成接入。读取工具不进入场景修改预览事务。

首版检索采用受控分类、中文/英文别名和关键词加硬条件过滤；建立固定样本评估，再依据实际召回问题增加向量检索或重排。向量相似不能覆盖“必须是圆桌”“宽度不超过 1.2 米”等明确条件。

搜索可返回近似候选，执行阶段不静默模糊替换 ID。多个同样合理候选时，复用 ask_user 或带缩略图的候选选择。库里没有圆餐桌时明确告知，可建议其他选项，不直接放入方桌。查询建议和错误解释按用户语言展示；ID 和枚举维持稳定。

## 8. 存量迁移与实施顺序

| 阶段 | 具体工作 | 完成条件 |
| --- | --- | --- |
| P0：目录基础 | 定义 AssetDefinition 及款式/材质能力字段；迁移 111 项及中文字典；统一 UI/AI 数据源；核对 MCP 差异；修正挂载摘要；加入中英文检索；禁止执行时静默模糊替换 | 旧 ID、外观、坐标和场景加载不变；同名歧义可见，中英文找到同一模型 |
| P1：入库闭环 | GLB 上传、草稿、几何检查、预览校正、本地持久化、发布事件；文字 AI 资料补全；版本绑定；精确调用；基础批量列表 | 新模型无需改 TS 文件，发布后立即可检索/试摆，重开可用 |
| P2：材质与换款 | 实际材质部位清单、材质方案、产品/款式关系；兼容替换候选；手动和 AI 共用替换事务；修正材质工具契约 | 可换部位不会空操作；换款保持身份与对齐；失败、撤销、重开均可恢复 |
| P3：视觉与批量效率 | 独立图像元数据接口、视觉配置能力、3—4 视图、字段证据与人工锁定、批量规则、识别缓存与失败重试 | 随机文件名模型可由视觉辅助完成资料；不支持视觉时明确降级 |
| P4：规模和交换 | search_assets/get_asset 全链路、检索评测、按需重排、完整资源包导入导出、跨环境验收 | 大目录无需全量提示词；新环境资源不缺失 |

P0—P1 可以作为入库内部试用版，当前讨论的材质与换款范围还需完成 P2。视觉识别按 P3 单独验收，不阻塞人工入库；承诺跨环境使用前必须完成 P4 中的资源交换验收。资源包未完成前明确标记仅当前宿主可用，不以浏览器刷新成功代替可携带性验收。

现阶段没有必须由用户先回答才能启动 P0 的问题。默认采用当前本地优先架构、静态 GLB 首版、用户可自建分类、草稿与发布分开；旧项目保持原绑定，AI 生成建议后由用户在入库界面确认。组织共享权限、更多源格式和商业规格管理属于后续范围选择，不把它们当成当前基础改造的前置条件。

首个纵向试点采用普通家具、吊顶物件、墙侧物件，以及一组带可换部位的壁炉和一个不同几何的壁炉。壁炉试点资源须实际准备和适配，当前目录并没有经过验收的完整同款系列；不能仅用虚构目录记录证明替换成功。先通过试点，再扩展到全部资产和批量处理。

迁移保留原始文件和旧变换。先给现有条目补语义与多语言，不批量重写尺度/朝向。MCP 与 UI 同 ID 的差异先生成报告，优先保留当前编辑器行为并用实际几何核查，不能任选一份视为正确。

建议代码落点（新增模块名称为方案建议）：

- `packages/core`：资产定义、放置规则和版本引用的纯数据契约；不引入 Three.js 或宿主文件操作。
- `packages/viewer`：复用加载/渲染；如需新增预览渲染能力，保持通用，不引用入库 UI 状态。
- `packages/editor`：共享目录适配、现有模型面板、检索工具、语言显示、放置与 AI 预览接入。
- `apps/editor`：入库向导、导入任务、文件/数据库服务、资源路由和 AI 元数据端点。
- `packages/mcp`：共享目录适配；消除静态重复资料，维持无浏览器依赖。

## 9. 验收与质量门槛

“可供 AI 使用”不根据 AI 的一句“识别完成”判定，而要求资源可加载、ID/版本可解析、基本语义齐全、几何和安装规则通过检查；存在关键未确认字段的条目保留草稿。对低置信但非关键的外观字段允许未知。

| 场景 | 预期结果 |
| --- | --- |
| 中文名/英文名/别名搜索 | 命中同一 ID；语言切换不修改场景名称和参数 |
| 只有无语义文件名 | 不凭文件名猜定；视觉辅助或用户说明生成资料 |
| 圆桌/方桌、餐桌/茶几相近 | 满足明确条件；不满足则返回无结果或询问 |
| 同名不同款、重复字节 | 同名可区分，重复文件可复用，ID 不冲突 |
| 新建、改名、移动分类 | 无循环和悬空引用；继承规则可见；新增语义不能伪造新执行能力 |
| 同款换材质、未知部位 | 已适配部位可见地更新；不存在的部位明确拒绝；保存重开仍保留 |
| 不同尺寸款式原位替换 | 保留实例身份及适用归属，锚点对齐，空间检查有效；不默认非均匀拉伸 |
| 不兼容宿主、附着子物件、资源加载失败 | 不留下半替换状态、不删除子对象，明确显示限制 |
| 换款的预览、取消、撤销和重做 | 单次事务恢复旧资产、版本、材质、变换和关系；2D/3D 一致 |
| 厘米导出但按米解释 | 尺寸异常可见并可校正；不静默缩放后直接发布 |
| 吊顶灯、墙侧灯、嵌墙门窗 | 正确宿主和锚点；无宿主不错误放地面；2D/3D 行为一致 |
| 桌面摆放及实例缩放 | 使用实际承载高度与最终尺寸，避免穿模/双重缩放 |
| 草稿/发布/下架/更新版本 | UI 与 AI 状态一致，草稿不被常规添加工具使用，旧场景不被新版本替换 |
| 入库后立即调用、切换项目 | 无需重启，作用域正确；临时场景条目不会误成公共资产 |
| 视觉接口不支持/超时/无 Key | 手工与文字工作流继续，草稿保留，可针对失败项重试 |
| 中途崩溃、重复发布 | 无悬空可用记录，无重复资产，批次能恢复 |
| 保存重开、撤销/重做 | 实例、材质、资源和版本仍可用 |
| 干净浏览器/另一环境导入 | 所需字节随包恢复，不能依赖旧 IndexedDB 或短期 blob URL |
| 大量条目 | 分页搜索，提示词不溢出，不扫描全量磁盘，不反复对相同模型收费识别 |

先用现有 111 项建立中文/英文固定查询集，并新增 20 个不同来源模型作为试点，覆盖上述场景。自动测试分别报告：精确 ID 解析/版本一致性、发布与持久化通过率、检索 Recall@5、AI 最终选择正确率、错误拒绝/澄清率和摆放成功率。建议精确引用、状态隔离、存储重开等确定性检查全部通过；语义指标先测基线后制定阈值，不能将模型自评当结果。

验证同时包括契约/迁移/检索测试和真实浏览器加载、2D/3D 操作、一次预览确认/撤销、干净环境资源恢复；模拟协议测试不能代替至少一条选定视觉配置的真实调用。

## 10. 外部调研依据

以下为官方或项目维护方资料，核查于 2026-09-20；工具选型为建议，尚未安装或完成与本项目的兼容验证。

- [Khronos glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)：米制、Y 轴向上；extras 可携带应用数据，但语义主记录建议仍由目录管理，便于检索、版本和多语言更新。
- [Khronos glTF Validator](https://github.com/KhronosGroup/glTF-Validator)：提供格式、引用、二进制和部分扩展检查及 JSON 报告，适合入库格式校验；不能判断物件用途或替代实际渲染。
- [glTF Transform CLI](https://gltf-transform.dev/cli)：提供 inspect 和优化处理，可用于资源分析及可选压缩。原始文件保留，优化输出作为派生资源，通过当前加载器与视觉回归再发布。
- [Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)：支持 glTF，并提供 Draco/KTX2/Meshopt 解码适配；项目已存在对应加载封装，应复用并测试导入模型的具体扩展。
- [Gemini 图片理解](https://ai.google.dev/gemini-api/docs/image-understanding)：验证“多张渲染图 + 文字”作为识别输入的可行接口模式，不表示当前系统已经接入或任何配置都能用。
- [Gemini 结构化输出](https://ai.google.dev/gemini-api/docs/structured-output)：验证按 JSON Schema 输出分类资料的技术路径；结构正确仍不代表语义正确，应用层继续校验。

推荐从 P0 的精确引用、多语言检索和能力一致性开始，随后贯通 P1 入库闭环及 P2 壁炉材质/换款试点，再扩展批量与视觉。每阶段按实际运行证据验收，不把资料字段齐全或工具调用成功当作画面与存储正确的证明。
