# 内置 AI 复用于模型评估和入库

核查日期：2026-09-20。本文是当前实现核查与接入设计，未实施新入库功能。用户已确认现有 AI 在真实工作；本轮通过代码调用链和本地模拟测试验证可复用部分，没有再次调用外部 AI 或修改用户场景。

## 1. 结论

现有内置 AI 可作为模型入库的资料助手和流程入口。已有配置、协议适配、多轮工具调用、提问、预览、执行结果回传及撤销基础，新增模型不需要重新训练语言模型。

迁移应分为三部分评估工作量：

| 工作 | 复用程度 | 本次判断 |
| --- | --- | --- |
| 根据用户说明和程序测量结果生成名称、分类、标签与缺项建议 | 高 | 可先增加一个结构化分析请求，回填入库草稿，不必先扩充整套对话工具 |
| 已登记新模型被现有 AI 调用并放入场景 | 高 | 已有自定义场景资产刷新与再次创建的通过测试；还需把永久目录接到同一读取入口 |
| 未知模型看图识别、真实文件永久入库、材质适配和原位换款 | 部分 | 分别缺少图像请求、资产存储/发布、部位元数据与替换事务；仅修改提示词不能补齐 |

## 2. 当前真实主链

当前独立应用挂载的是 `AIProvider → AIPanel → AIChatPanel`。聊天由 `runAgentLoop` 调度，经 `AIRuntime.transport` 调用 `/api/ai/chat`，由服务端读取保存的 AI 配置并适配上游协议。模型返回工具调用后，在客户端做语义和空间校验，再通过原生场景适配器预览和提交。

链路：

```text
用户说明 + 场景摘要 + 模型目录摘要
  → 已保存的 AI 配置与服务端协议适配
  → 文字回复 / 工具调用
  → 参数检查 + 目录解析 + 场景/位置校验
  → 预览 → 确认或用户启用的自动应用 → 原生场景事务
  → 执行结果返回 AI → 后续调用或完成回复
```

当前声明 56 项工具，参数白名单与上游工具表来自同一份 `toolDefinitions`。这不表示 56 项都经过真实外部 AI 和浏览器验收。`integrations/ai/scene-tools.ts` 还保留一个只支持少数家具操作的模块，它不是当前面板全部能力；不能据其中五个 schema 把实际主链误判为只有五种工具。

## 3. 可以复用的现有能力

| 现有能力 | 已核实的实现 | 用于入库时的接法与边界 |
| --- | --- | --- |
| 已保存 AI 配置、模型选择、思考参数 | 同一 profileId 在服务端取得配置；密钥不需要传回浏览器 | 入库分析复用当前选择，不要求重复配置；选择状态需开放给入库 UI |
| OpenAI-compatible、Anthropic、Gemini 请求与流式返回 | `providerRequest`、`readProviderCompletion` | 可复用文字与工具传输；协议分支存在不代表当前选中模型具备视觉能力 |
| 目录读取与资产解析 | `CatalogProvider.resolveSlug/generateSummary/refresh` | 接入持久化目录后继续使用；当前默认源是内置目录加当前场景 item |
| 场景读取和上下文 | 每轮重新生成楼层、房间、结构与物件摘要 | 可用于评估摆放适配和试摆；当前数据主要是结构化文字，不是网格视觉理解 |
| 添加、移动、缩放、删除物件 | `add_item/move_item/update_item/remove_item` | 已发布普通模型可复用；`add_item` 创建场景实例，不写入永久模型库 |
| 建筑与机电操作 | 墙、门窗、楼板、屋顶、楼梯、房间、围栏、风管/水管等工具及执行分派 | 说明工具体系可扩展；不能把参数化工具自动转换成任意外部模型的能力 |
| 追问和候选方案 | `ask_user`、`propose_placement` | 可复用交互模式询问用途、分类歧义和安装位置；入库草稿仍需新的数据契约 |
| 预览、取消、确认、错误回传和撤销 | `SceneEditAdapter` 与 AI 预览管理器 | 入库后的试摆可以复用；资产发布用资产事务，不能假装成场景节点事务 |
| 对话总结、停止与错误处理 | 同配置摘要接口，AbortSignal 贯穿请求 | 复用到长批次的取消/错误显示；批次恢复与幂等发布仍需资产任务记录 |

不能当作现成入库功能的相近入口：

- `add_scan` / `add_guide` 的工具设计是通过 URL 添加场景参考节点，不完成分类、版本管理和模型目录发布。后续 [扫描专项核查](scan-import-audit.md) 已复现 `add_scan` 执行器的 scale 类型错误，并发现本地 URL 和透明度契约不一致；不能把工具声明当作该路径已可用。该专项结果不否定普通 `add_item` 的通过测试。
- `save_room_preset` / `insert_room_preset` 虽然在工具表里，但独立应用默认 provider 返回不可用；本轮没有找到应用注入持久化 provider。它们不是可直接借用的模型库后端。
- `saveAsset` 把文件放进浏览器 IndexedDB 并返回 `asset://`。这可作为本机预览基础，不构成宿主持久化目录或跨电脑可携带性。

## 4. “新模型能够继续被现有 AI 调用”已有直接证据

现有 [目录刷新集成测试](../../tests/integration/ai-full.test.ts:292) 执行了以下行为：

1. 创建一个原目录没有的自定义 `ItemNode`，带稳定 ID、名称、文件引用、分类和尺寸。
2. 确认旧目录缓存尚未包含它。
3. 刷新缓存后，通过 ID 和名称解析到新资产，AI 目录摘要出现新资产名称。
4. 通过原有 `add_item` 校验、预览、提交，再生成该资产的第二个实例。

此测试本轮通过。它证明目录接入和现有添加工具具有扩展能力；测试使用占位 URL，不证明文件真实加载、尺寸真实、外观识别正确或永久入库已经存在。

目前 `CatalogProvider` 虽声明可选 `subscribe`，默认实现不提供它，也未发现当前主链消费该订阅。新模型发布时必须实际更新 UI/AI 共同读取的数据并失效目录摘要缓存，不能只增加一个订阅方法便声称发布后立即可见。

## 5. 需要补齐的边界

### 5.1 AI 现在没有收到模型图片

当前请求 `message.content` 为字符串，三个协议分支发送文字和工具消息；没有图片内容契约。前后截图捕获为浏览器 blob URL，存入聊天消息用于用户查看，并未加入上游请求。

因此可以复用截图渲染的一部分能力，但模型预览、多视图生成、图像字节传输、图片大小限制和实际视觉能力验证都要补充。当前模型是否支持视觉，应按用户选中的具体配置验证，不能依据厂商名或模型名推定。

依据：[消息契约](../../packages/editor/src/integrations/ai/contracts.ts:49)、[请求构造](../../packages/editor/src/components/ai/ai-agent-loop.ts:694)、[截图回调](../../packages/editor/src/components/ai/preview/preview-overlay.tsx:188)。

### 5.2 场景请求不能直接充当入库请求

当前传输需要已绑定项目、场景适配器和 `sceneRevision`；场景发生变更会使返回结果过期。评估入库资料应绑定 `importId + draftRevision`，用户移动一张椅子不应让模型资料分析失效，用户修改待入库模型的尺寸则必须让旧建议失效。

现有 `providerRequest` 的工具开关是布尔值，启用后发送全部场景工具；结果校验也使用场景工具白名单。正式增加入库对话工具时，应同时扩展按任务选择工具集、参数校验、结果解析、调度与回传。仅增加一个工具描述无法完成接入。

### 5.3 程序检查和 AI 评估分工

| 内容 | 执行者 | 输出 |
| --- | --- | --- |
| 文件 hash、格式与依赖、实际边界、网格和材质统计、资源是否加载 | 导入程序和渲染检查 | 可核查事实；AI 不得改写测量值或伪造通过 |
| 名称、分类候选、别名、用途、风格、与现有款式的关系建议 | 现有 AI + 用户说明；外观识别另需图片 | 建议、理由、未知项；相似不自动等于同产品 |
| 比例是否符合实际产品、用途歧义、安装方式、关键资料确认 | 用户依据模型和来源资料确认 | 锁定字段，后续分析不覆盖 |
| 是否允许发布 | 确定性入库规则 | 必要字段与资源检查通过；AI 评语不能跳过校验 |

## 6. 最小接入方案

下列端点、工具名和契约均为拟新增内容，不是当前已经存在的功能。

### 第一步：单次分析回填表单，先复用当前 AI 配置

在入库向导提供“AI 帮我整理”操作，新增 `POST /api/ai/assets/analyze`：

- 请求携带 `profileId`、可选 model/thinking、locale、importId、draftRevision、用户说明。
- 服务端依据草稿加载程序测量事实和有效分类表；AI 只返回名称、别名、分类候选、属性、放置模板建议和待确认项。
- 复用 `getProfileStore`、`providerRequest` 和 `readProviderCompletion`；首版关闭场景工具，按新的元数据 schema 校验返回文字中的结构化结果。无须让每一次填表都跑多轮场景 Agent。
- 只应用允许的建议字段，保留来源和人工锁定状态；不允许 AI 修改 ID、文件位置、hash、测量结果和发布状态。
- 更新草稿前检查 draftRevision；失败或取消保持已有表单内容。未配置 AI 时仍可人工入库。

相同配置可以为场景聊天和资料分析服务；请求目的、上下文和写入目标分开。当前聊天选择位于应用组件内部，需要提取一个共享配置选择接口，不能为入库另存一份密钥。

### 第二步：完成真实入库，再接通现有添加工具

```text
用户提供模型文件
  → 导入程序保存草稿、检查文件、测量、生成预览
  → 现有 AI 生成资料建议
  → 用户确认必要项
  → 资产服务校验、保存版本并发布
  → 更新共享目录 + 失效 UI/AI 缓存
  → 原有 add_item 按准确资产 ID 试摆
```

先以当前 `CatalogProvider` 作为 AI 接口边界，把统一资产服务投影成现有运行时资产，不重写正常工作的摆放执行器。模型库面板也读取同一服务。宽松匹配只用于候选检索，提交创建时使用明确 ID 和版本。

### 第三步：同一个聊天框也能发起入库

在文件已由用户提供并取得 importId 后，增加少量资产工具，例如 `inspect_import`、`propose_asset_metadata`。这些工具查询或更新同一入库草稿；必要时沿用 `ask_user` 的问答体验。用户说“帮我加入模型库”时进入同一向导，不另做一条存储通道。

初版的发布由向导按钮调用统一资产服务即可。以后增加 `publish_asset` 工具时，也必须检查相同的草稿版本、用户确认和发布条件；场景的自动应用开关不能默认授权发布资产。

只读资产工具和草稿工具应单独分派并回传结果，不能落入当前“其余工具都作为场景修改”的分支。资产发布撤回与场景撤销也要区分，避免撤销试摆顺带删除其他项目仍需使用的库文件。

### 第四步：视觉识别和材质/换款能力

在同一 profile 体系中补图像契约和能力验证，提供多视图后再声称能评估未知外观；材质部位和原位换款按 [总体实施方案](model-ingestion-ai-plan.md:159) 独立补齐。它们复用 AI 调用基础，但不是当前 `add_item` 自带的能力。

## 7. 本轮验证与后续验收

本轮执行现有三个测试文件：

```sh
bun test apps/editor/lib/integration-ai/provider.test.ts apps/editor/lib/integration-ai/protocols.test.ts tests/integration/ai-full.test.ts
```

结果：43 通过、0 失败、273 次断言，Bun 1.3.14。覆盖工具声明与解析、三种协议构造/结果解析、多轮调用与确认、停止、目录刷新、场景事务、部分结构操作和撤销。上游响应由测试替身提供，没有使用实际密钥。测试中的存储不可用和 runtime 替换提示来自无浏览器存储及测试注入，不是生产界面验证。

首个接入验收应包括：

- 中文用途说明 → AI 返回有效分类 ID 和可编辑名称；含歧义时给候选，不发明分类 ID。
- 文件损坏、单位异常、缺失依赖 → 程序指出原因，AI 不能直接发布。
- 用户已修改或锁定的草稿 → 旧分析结果不能覆盖。
- 发布 → 不重启即可在模型库和 AI 目录找到同一资产；旧的同名模型仍可准确选择。
- 试摆 → 实际文件可渲染、放置校验通过、可撤销，保存重开资源可用。
- 视觉配置不支持或网络失败 → 文字/人工路径可继续，不能误报已看图识别。

确定性接口与数据一致性通过后，再用用户选中的实际配置跑端到端资料分析和新增模型试摆。不能以本轮 43 项模拟测试代替新功能验收。
